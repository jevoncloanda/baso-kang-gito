# Baso Kang Gito

- Real bookkeeping for an Indonesian family bakso business. Prioritize reliable records, simple parent-friendly flows, large touch targets, phone/tablet layouts, and accessibility. English is the default development UI; complete natural Bahasa Indonesia remains available for family use.
- Root `compose.yaml`; native Kotlin/Compose/Material 3 in `android/` (one app module); Node 22 LTS, TypeScript, Fastify, Kysely and PostgreSQL in `backend/`. npm lockfile is authoritative. API contract: `docs/openapi.yaml`.
- Extend existing ownership and patterns. No speculative frameworks, services, DI, navigation, business tables or sync engine. No `infra/`, `apps/`, `packages/` or future `web/` scaffolding.
- Before editing, trace the affected behavior and callers. Preserve unrelated files and user changes. Never reset data, install system tools/SDK packages, change global settings, deploy, commit, push or create a PR without explicit instruction.
- Sales and cash received differ. Debt payments must not duplicate sales; platform settlements have separate dates; event deposits are not completed sales; withdrawals differ from expenses. Review the financial model before implementing it. Future writes need stable IDs, idempotency, transactions and retry safety.
- Android bookkeeping uses Room with an atomic local record/outbox write and bounded development sync through the single API. Preserve operation IDs, expected versions, acknowledgment ordering, pull cursors and explicit conflict review. Future POS and bookkeeping share the financial/reporting model; do not expand sync without a scoped task.
- Buku Harian proposal and acceptance: `docs/buku-harian.md`. Platform notebook amounts are confirmed net earnings after platform fees; do not double-deduct fees or count payouts as new sales. Review the proposal before business migrations.
- Android brand: Warm Slate & Terracotta. Anchors: slate navy `#303B53`, terracotta `#BD6254`, ivory `#F8F5F1`, white, muted gold `#D8AC70`, text `#253047`. Slate owns actions, active navigation and selection; terracotta is a restrained accent, gold is reserved for meaningful distinction. Use contrast-adjusted variants rather than forcing anchor colors onto small text.
- `ui/BasoTheme.kt` owns light/dark Material semantic colors, type, spacing and shapes. Light uses ivory/white; dark uses deep neutral/slate surfaces with lighter slate controls and warm accents. Screens consume `MaterialTheme.colorScheme`; keep brand hex values out of components. Financial states need explicit labels and separate semantic meaning: errors use error roles, never terracotta merely because it resembles red. Preserve neutral receipt/payment labels; do not invent success/warning/sync states before their behavior exists. Extend existing Material 3 components and outline vectors; no gradients, heavy shadows, nested cards or new theme frameworks. Verify text contrast (4.5:1) and active control/focus contrast (3:1) in both themes.
- Android labels, validation and accessibility text belong in `res/values/strings.xml` plus `res/values-in/strings.xml`; no user-facing literals in Composables. Preserve the EN/ID selector, native per-app language support and drafts during recreation. Keep raw integer rupiah separate from formatted display; preserve stable shopping-row IDs and IME/focus behavior.
- Adapt to available width: navigation bar below 600 dp, rail from 600 dp; split notebook summary/history when content has at least 840 dp. Forms/details stay within 640 dp. Keep identical functionality, 48 dp minimum targets, 56 dp primary actions, keyboard insets, accessible labels, and saveable drafts across resizing/recreation.
- `MainActivity` gates the Room-backed `FunctionalNotebook` with trusted-device enrollment and a local PIN; debug/test fixtures must never enter real reports. Financial APIs require unique device credentials; the shared development token controls only the isolated port-3001 test helper. Debug sync is loopback; configured release sync requires HTTPS. Keep authorization outside Room and portable backups, preserve pending records on access failures, and never bypass enrollment or PIN recovery approval. Do not use this build as the family's sole ledger without reviewed deployment and tested backup/recovery. Verify phone/expanded rendering, large text and physical-device interactions; never label density simulation as physical-tablet testing.
- Keep secrets in ignored `.env` files. Never log connection strings, credentials or sensitive records. Bind local services to loopback; no public database or unauthenticated API exposure.
- Run backend typecheck, build and unit tests for backend edits. Run integration tests against local PostgreSQL for database/migration changes. Append migrations; never edit an applied migration. Do not drop data to make checks pass.
- For Android edits, run `assembleDebug`, `lintDebug`, `testValidationUnitTest` when SDK components exist. This checkout generates tests for the separate `.validation` package (`testBuildType = "validation"`); use `connectedValidationAndroidTest` only with an available physical device and the isolated test API on port 3001. Do not clear/uninstall the real notebook or use emulators without explicit instruction. Report blocked/unexecuted checks honestly.
- Agent tooling is separate from project prerequisites. Where RTK is provided, use `rtk <command>` or `rtk proxy <command>` according to the active host's instructions. Keep personal wrappers, usernames, HOME overrides and agent configuration out of general onboarding; do not change global settings.
